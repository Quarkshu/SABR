实验方案 v0.2
对应开发计划：development_plan.md v1.2
日期：2026-04-21

一、实验定位与目标
1.1 文档定位
本版实验方案与 development_plan.md v1.2 一一对应，目标不再只是描述“希望做什么实验”，而是明确“当开发计划全部完成后，实验一到实验六均可通过配置、命令和脚本直接执行”。

本方案的完成定义如下：
1.	六个实验均有可执行配置文件、标准运行命令和结果输出目录规范。
2.	单播、多播、局部修复、冗余传输四类机制均可通过日志和统计结果量化。
3.	实验运行不依赖手工改代码，仅通过配置、CLI 参数和批量脚本切换场景与开关。
4.	实验结果同时支持机器可读导出（JSON / CSV）与图表生成。

1.2 总体目标
1.	验证单播 SABR/CGR 三阶段路由流程的正确性，包括接触图构造、路由规划、路由验证、路由选择与逐跳重计算。
2.	验证多播传播计划机制的正确性，包括共享前缀合并、分叉点复制、局部传播计划裁剪与目的节点交付。
3.	验证中间节点在 Contact 不可用时，对受影响目的节点子集进行局部修复的有效性。
4.	验证冗余传输机制在高风险场景下对交付率与鲁棒性的提升效果，并确认副本数量和额外开销受到阈值约束。
5.	评估系统在不同网络规模、业务负载、TTL 约束、Contact 失效和动态计划更新条件下的性能与资源开销。
6.	保证实验结果可复现、可批量运行、可自动聚合并可用于毕设报告或论文图表输出。

1.3 具体目标
•	从正确性角度，确认系统输出符合需求规格、设计文档和参考场景预期。
•	从效率角度，评估交付率、端到端时延、跳数、Contact 利用率、共享前缀节省率等关键指标。
•	从鲁棒性角度，评估 Contact 失效、动态 ContactPlan 更新和局部修复对系统行为的影响。
•	从创新性角度，重点验证受控冗余传输机制在可靠性提升与额外开销之间的平衡效果。

1.4 与开发计划的对应关系
•	阶段 3A / 3B / 3C：提供离散事件仿真、流量生成、故障注入和动态计划更新能力，支撑实验一、二、四、五、六。
•	阶段 4A / 4B：提供输入配置、日志、统计、JSON / CSV 导出和结果聚合格式，支撑全部实验。
•	阶段 5：提供单播端到端基线和参考场景验证，直接支撑实验一和实验二。
•	阶段 6A：提供多播传播计划构造和“拆成多个独立单播”的对照基线，直接支撑实验三。
•	阶段 6B：提供多播执行、局部修复和共享前缀容量控制，直接支撑实验四和实验六的多播组。
•	阶段 7A：提供增强功能开关和组合测试，直接支撑实验六中的“单播 + 增强功能”组。
•	阶段 7B：提供冗余传输、首达去重和冗余统计，直接支撑实验五和实验六中的冗余组。
•	阶段 8A / 8B：提供批量实验运行器、CLI、结果目录规范、绘图脚本和实验手册，保证实验方案 100% 可执行。


二、实验环境配置与运行前提
2.1 软件环境
实验环境采用如下配置：
•	C++ 标准：C++17
•	编译器：GCC 8+ / Clang 7+ / MSVC 2019+
•	构建工具：CMake 3.16+
•	测试框架：Google Test
•	批量实验与结果聚合：Python 3.8+
•	核心依赖：C++ 标准库

2.2 计划完成后的运行组件
在 development_plan.md v1.2 全部完成后，实验运行环境应至少包含以下组件：
•	可执行程序：build/sabr.exe
•	CLI 子命令：run-scenario、run-experiment、export、plot
•	批量运行脚本：scripts/run_experiments.py
•	结果聚合脚本：scripts/aggregate_results.py
•	可视化脚本：plot_topology.py、plot_timeline.py、plot_utilization.py 以及实验对比绘图脚本
•	输入配置目录：configs/experiments/
•	结果输出目录：results/

2.3 标准构建与运行流程
Windows / MinGW 示例流程如下：
1.	配置工程：cmake -S . -B build -G "MinGW Makefiles"
2.	编译工程：cmake --build build
3.	运行单场景：build/sabr.exe run-scenario --config <scenario.json> --output <result_dir>
4.	运行批量实验：python scripts/run_experiments.py --experiment <matrix.json> --executable build/sabr.exe --output <result_dir>
5.	聚合结果：python scripts/aggregate_results.py --input <result_dir> --output <aggregate_dir>
6.	生成图表：build/sabr.exe plot --input <aggregate.json> --output <plot_dir>

2.4 结果目录规范
每个实验应遵循统一输出目录结构：

results/

其中：
•	logs/：Phase 1 / 2 / 3、commit、局部修复、冗余决策等详细日志
•	stats/：交付率、时延、跳数、利用率、局部修复、冗余命中等原始统计
•	exports/：JSON / CSV 导出和汇总表
•	plots/：拓扑图、时间线图、利用率图和对比图


三、预期效果
3.1 单播部分预期效果
1.	系统能够根据 Contact Plan 正确构造接触图并生成候选路由。
2.	系统能够基于 ETO、PBAT、RVL 等指标完成路由验证与筛选。
3.	系统能够在不同节点执行逐跳重计算，而不是沿用源节点路径。
4.	在参考场景下，单播行为与需求文档中的测试预期相符。

3.2 多播部分预期效果
1.	源节点能够将多个单播最优路径合并成多播传播计划。
2.	多播共享前缀合并后，整体容量占用应低于“将多播拆成多个独立单播”的方式。
3.	中间节点在分叉点处能够按目的节点子集复制并转发。
4.	Contact 不可用时，中间节点能够只对受影响的目的节点子集进行局部修复，而不是全局重算。

3.3 冗余传输部分预期效果
1.	在高风险场景下，单播冗余的 SINGLE_BACKUP 和 MULTI_BACKUP 模式能够提高交付率或降低失败率。
2.	在多播场景中，TRUNK_ONLY 模式能够在不造成副本爆炸的前提下提高干线可靠性。
3.	冗余副本数量与额外容量开销应受到 max_extra_copies、容量保护阈值和 TTL 裕量约束。
4.	目的节点能够基于 origin_bundle_id 完成首达去重，并记录重复副本丢弃与冗余命中统计。

3.4 整体系统预期效果
1.	系统能够输出完整的路由日志、交付统计、Contact 利用率统计、局部修复记录与冗余统计。
2.	系统在中等规模实验场景下能够稳定运行，并支持固定随机种子重复实验。
3.	系统能够支持单播、多播、局部修复、冗余四类机制的对比实验。
4.	系统能够通过 CLI 和脚本完成单场景运行、参数扫描、结果聚合和图表生成。


四、实验方法
4.1 核心方法
本实验采用离散事件仿真方法，以 Contact Plan 为网络时变拓扑输入，模拟 Bundle 在空间 DTN 网络中的生成、排队、转发、到达、交付、去重、过期和失败过程。

实验通过设置不同的网络规模、业务负载、TTL、Contact 容量、失效场景、动态计划更新和机制开关，比较不同路由机制下系统的行为差异。批量实验由统一配置文件和批量运行脚本驱动，保证实验可复现和可重复。

4.2 技术路线（与开发计划一一对应）
1.	阶段 3A / 3B：构建离散事件调度、BPA、流量生成与单播基础仿真能力。
2.	阶段 3C：引入 Contact 失效、关键干线移除和动态 ContactPlan 更新。
3.	阶段 4A：建立 Contact Plan、流量、多播组、故障注入和冗余模式的统一配置格式。
4.	阶段 4B：接入路由日志、局部修复日志、冗余日志、统计导出与汇总格式。
5.	阶段 5：运行单播 SABR/CGR 基线实验，验证单播正确性与参考场景符合性。
6.	阶段 6A / 6B：加入多播传播计划、多播执行和局部修复能力，形成多播对照实验。
7.	阶段 7A：接入 One-Route-Per-Neighbor、Queue-Delay、Anti-Loop 等增强功能，完成机制消融的增强组。
8.	阶段 7B：加入冗余传输与去重能力，形成实验五和实验六中的冗余组。
9.	阶段 8A / 8B：通过 CLI、批量运行脚本、聚合脚本和绘图脚本完成实验执行闭环。

4.3 自变量（实验约束）
（1）网络规模约束
•	节点数：5、10、20
•	Contact 数：20、50、200
•	仿真时长：1h、3h、6h

（2）流量负载约束
•	Bundle 数量：50、200、1000
•	Bundle 大小：1 KB、10 KB、100 KB
•	生成模式：单次 / 批量 / 周期生成
•	单播与多播比例：100:0、70:30、50:50

（3）时间约束
•	TTL：宽松 / 中等 / 紧张
•	Contact 窗口长度：长 / 中 / 短
•	OWLT margin：固定值或多组对比

（4）Contact 资源约束
•	传输速率：高 / 中 / 低
•	Contact 容量：充足 / 中等 / 紧张
•	是否存在瓶颈 Contact：是 / 否

（5）扰动约束
•	Contact 失效概率：0%、5%、10%、20%
•	是否发生动态 Contact Plan 更新：是 / 否
•	是否人为移除关键干线 Contact：是 / 否
•	随机种子：固定种子 / 种子组

（6）机制开关约束
•	单播增强功能：开 / 关
•	多播传播计划：开 / 关
•	多播局部修复：开 / 关
•	冗余传输模式：NONE / SINGLE_BACKUP / MULTI_BACKUP / TRUNK_ONLY

4.4 统计指标定义
•	交付率：delivered_bundles / created_bundles
•	多播全组完成率：完成全部目的节点交付的多播组数量 / 多播组总数
•	平均时延：已交付 Bundle 的 delivered_time - creation_time 的均值
•	平均跳数：已交付 Bundle 的实际 route_path 长度均值
•	共享前缀节省率：1 - multicast_committed_volume / split_unicast_committed_volume
•	交付保持率：repair_scenario_delivery_ratio / no_failure_delivery_ratio
•	冗余收益：delivery_ratio_with_redundancy - delivery_ratio_without_redundancy
•	冗余开销比：extra_committed_volume / baseline_committed_volume
•	收益成本比：redundancy_benefit / redundancy_overhead_ratio


五、实验数据与配置
5.1 输入数据类型
实验运行至少需要以下配置输入：
•	Contact Plan：ION 或 JSON 格式，包含 contact、range、contact_id 分配信息
•	仿真参数：起止时间、OWLT margin、随机种子
•	流量配置：源节点、目的节点或多播组、生成模式、生成时间、Bundle 大小、TTL、优先级
•	多播组定义：组标识、成员节点、源节点
•	故障注入配置：失效时刻、失效 Contact 集、失效概率、关键干线移除规则
•	冗余配置：模式、max_extra_copies、风险阈值、最小差异度、容量保护阈值、TTL 裕量阈值
•	实验矩阵：节点数、Contact 数、负载、机制开关与对比组组合

5.2 配置文件组织
建议目录结构如下：

configs/
	experiments/
		exp1_unicast_correctness/
		exp2_unicast_scale/
		exp3_multicast_plan/
		exp4_multicast_repair/
		exp5_redundancy/
		exp6_ablation/

每个实验目录至少包含：
•	baseline 场景配置
•	对照组配置
•	参数扫描矩阵配置
•	最小 smoke case 配置

5.3 输出文件组织
每个实验结果目录至少包含：
•	logs/route_decisions.jsonl：Phase 1 / 2 / 3 / commit / reroute / redundancy 明细
•	logs/multicast_plan.jsonl：传播计划、分叉、局部修复与子树裁剪记录
•	logs/redundancy.jsonl：冗余触发、备份路径选择、去重与丢弃记录
•	stats/bundle_stats.json：Bundle 交付、失败、跳数、时延统计
•	stats/contact_utilization.json：Contact 利用率统计
•	stats/repair_stats.json：局部修复次数、影响范围和成功率
•	stats/redundancy_stats.json：冗余触发率、命中率、开销与收益
•	exports/*.csv：用于表格汇总与论文制图的导出文件
•	plots/*.png：自动生成的图表

5.4 代表性场景集
为保证计划完成后实验可直接执行，至少准备以下标准场景集：
•	小规模单播正确性场景：3 节点 / 3 Contact / 5 Bundle
•	REF-2 参考单播场景：5 节点参考拓扑
•	共享前缀多播场景：至少 1 条公共前缀 + 2 个以上分支
•	局部修复场景：含关键 Contact，且失效仅影响部分目的节点
•	高风险冗余场景：TTL 紧张、干线 Contact 容量紧张或终止时间逼近 ETO / PBAT
•	中等规模性能场景：20 节点 / 200 Contact / 1000 Bundle


六、实验设计
6.1 实验一：单播正确性验证实验
目的
验证单播 SABR/CGR 三阶段流程、显式提交与逐跳重计算是否正确实现。

前置阶段
阶段 3A、3B、4A、4B、5。

输入配置
•	小规模 Contact Plan
•	单播流量配置
•	关闭多播和冗余功能
•	关闭非必要增强功能，必要时单独做增量对比

标准命令
•	build/sabr.exe run-scenario --config configs/experiments/exp1_unicast_correctness/ref2_baseline.json --output results/exp1_unicast_correctness/ref2_baseline

输出
•	路由日志
•	交付统计
•	PBAT / RVL / ETO 明细
•	逐跳重算统计

关注指标
•	交付率
•	平均时延
•	平均跳数
•	路由失败率
•	逐跳重算次数

通过标准
•	接触图构造正确
•	候选路由满足排除规则
•	路由选择符合四级比较规则
•	到达下一跳后触发逐跳重算
•	与参考场景预期一致

6.2 实验二：单播负载与规模实验
目的
评估单播 SABR/CGR 在不同网络规模和流量负载下的性能、资源占用与运行时间。

前置阶段
阶段 3A、3B、3C、4A、4B、5、8A。

输入配置
•	不同节点数与 Contact 数的 Contact Plan
•	不同强度的单播流量
•	固定随机种子或种子组

标准命令
•	python scripts/run_experiments.py --experiment configs/experiments/exp2_unicast_scale/matrix.json --executable build/sabr.exe --output results/exp2_unicast_scale

输出
•	统计文件
•	Contact 利用率分布
•	仿真运行时间
•	聚合表与对比图

关注指标
•	交付率
•	平均时延
•	Contact 利用率
•	仿真运行时间

通过标准
•	矩阵中的全部场景均可直接运行
•	结果可批量聚合为统一格式表格和图表
•	中等规模场景能够稳定完成仿真，不出现异常崩溃

6.3 实验三：多播传播计划机制实验
目的
验证多播传播计划机制能否正确构造共享前缀，并节省资源。

前置阶段
阶段 4A、4B、6A、6B、8A。

对比方案
•	方案 A：将多播拆成多个独立单播
•	方案 B：使用多播传播计划

输入配置
•	多播组定义
•	相同源节点和成员节点集合
•	相同业务负载
•	关闭冗余机制

标准命令
•	python scripts/run_experiments.py --experiment configs/experiments/exp3_multicast_plan/compare_plan_vs_split.json --executable build/sabr.exe --output results/exp3_multicast_plan

输出
•	多播传播计划日志
•	副本生成与分叉日志
•	统计文件
•	共享前缀节省率对比图

关注指标
•	多播目的节点交付率
•	多播全组完成率
•	复制次数
•	共享前缀节省率
•	Contact 利用率

通过标准
•	传播计划构造正确
•	共享前缀场景下，传播计划方案的容量占用低于拆分单播方案
•	分叉与裁剪行为可由日志完整追踪

6.4 实验四：多播局部修复鲁棒性实验
目的
验证 Contact 不可用时，中间节点是否能够只修复受影响的目的节点子集。

前置阶段
阶段 3C、4A、4B、6B、8A。

输入配置
•	多播流量
•	含关键 Contact 的 Contact Plan
•	失效注入配置
•	关闭冗余机制，避免干扰局部修复归因

标准命令
•	build/sabr.exe run-scenario --config configs/experiments/exp4_multicast_repair/repair_with_failure.json --output results/exp4_multicast_repair/repair_with_failure

输出
•	局部修复日志
•	受影响目的节点子集记录
•	修复后的新传播计划
•	交付保持率统计

关注指标
•	局部修复次数
•	局部修复成功率
•	平均修复影响范围
•	交付保持率

通过标准
•	仅受影响的目的节点子集被重路由
•	未受影响分支不被错误重算
•	局部修复前后传播计划可由日志和编码版本追踪

6.5 实验五：冗余传输有效性实验
目的
验证冗余传输机制在高风险场景下对交付率和鲁棒性的提升作用，并评估额外开销。

前置阶段
阶段 3A、3B、3C、4A、4B、5、6B、7B、8A。

对比方案
（A）单播高风险场景
•	方案 A1：NONE
•	方案 A2：SINGLE_BACKUP
•	方案 A3：MULTI_BACKUP

（B）多播高风险场景
•	方案 B1：NONE
•	方案 B2：TRUNK_ONLY

输入配置
•	中高风险 Contact Plan
•	较紧张 TTL
•	中高负载流量
•	冗余模式、风险阈值、差异度阈值和副本数量上限配置

•	副本数量受 max_extra_copies 约束，不出现副本爆炸
•	至少一个代表性高风险场景中，冗余机制带来正向交付收益，且容量保护阈值生效
